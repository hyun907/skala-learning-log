# JavaScript 비동기 실행 모델: 데이터가 먼저 도착해도 끼어들 수 없다

## 개념 정의

JavaScript는 한 번에 하나의 코드만 실행한다(싱글 스레드). 그래서 오래 걸리는 작업은 브라우저나 런타임에 맡기고 자리를 비켜준 뒤, 호출 스택이 완전히 비었을 때 이벤트 루프가 결과를 다시 올려 이어서 실행한다.

여기서 비동기가 무엇이 아닌지가 먼저다. **비동기는 동시 실행이 아니다.** 기다리지 않을 뿐이다. 병렬처럼 보이는 건 네트워크 요청이나 타이머를 브라우저·OS가 대신 처리해주기 때문이고, 내가 쓴 JavaScript 코드 자체는 여전히 한 줄씩 돈다.

## 동작 원리

`await`를 만났을 때 실제로 일어나는 일은 세 단계다.

1. **`await`를 만나는 순간** — 뒤의 비동기 작업을 즉시 시작시키고, 그 `async` 함수의 실행을 일시 정지한다. 함수의 나머지 코드와 현재 상태를 통째로 보관해두고, 제어권을 호출한 쪽으로 돌려준다. 메인 흐름의 남은 코드가 계속 실행된다.
2. **작업이 끝났을 때** — 끼어들지 못한다. 싱글 스레드라 한 번에 하나만 실행 가능하다. 대신 나머지 코드가 마이크로태스크 큐라는 대기줄에 등록된다.
3. **메인 흐름이 완전히 끝난 직후** — 호출 스택이 비는 순간 이벤트 루프가 큐에서 꺼내 스택에 올리고, 흐름이 `await` 다음 줄로 복귀한다.

```
메인 흐름 실행 중 ──────────────────────▶ 끝 (호출 스택 비었음)
                                             │
  [비동기 완료] ──▶ 마이크로태스크 큐 대기 ──┘
                                             ▼
                                  이벤트 루프가 꺼내서 재개
```

`await`가 멈추는 건 그 `async` 함수 하나이지 페이지 전체가 아니다. 그리고 `async` 함수는 무엇을 `return`하든 항상 Promise를 반환한다. 일반 값을 반환하면 자동으로 감싸진다.

대기줄은 하나가 아니다. `setTimeout` 콜백이 들어가는 태스크 큐와 Promise 후속 처리가 들어가는 마이크로태스크 큐는 우선순위가 다르고, 마이크로태스크가 먼저 처리된다.

## 직접 확인한 예시

말로 읽으면 순서가 안 잡혀서 세 종류를 한 파일에 섞어 실행 순서를 찍어봤다(Node에서 실행. 출력 형식만 다를 뿐 브라우저 콘솔도 순서는 같다).

```js
console.log("1 동기");
setTimeout(() => console.log("4 setTimeout 0ms"), 0);
Promise.resolve().then(() => console.log("3 Promise.then"));
console.log("2 동기");

async function f() { return "값"; }
console.log("f() 반환:", f());
f().then(v => console.log("await 후:", v));
```

```
1 동기
2 동기
f() 반환: Promise { '값' }
3 Promise.then
await 후: 값
4 setTimeout 0ms
```

세 가지가 한 번에 확인됐다.

**0ms를 줬는데 `setTimeout`이 꼴찌다.** 지연 시간 0은 지금 실행하라는 뜻이 아니라 지금 돌고 있는 코드가 전부 끝난 뒤에 넣어달라는 뜻이다. 코드에는 두 번째 줄에 적혀 있지만 실행은 마지막이다.

**`Promise.then`은 동기 코드 다음, `setTimeout`보다는 앞이다.** 소스 순서상 `setTimeout`이 먼저 등록됐는데도 뒤집혔다. 마이크로태스크 큐가 태스크 큐보다 먼저 비워진다는 게 이 한 줄 차이로 드러난다.

**`f()`가 반환한 건 문자열이 아니라 `Promise { '값' }`이다.** `return "값"`이라고 썼는데도 그렇다. `async`를 붙이는 순간 반환값이 감싸지므로, 결과를 쓰려면 `await`나 `.then()`을 거쳐야 한다.

## 자주 발생하는 오류

- **`await` 없이 호출하고 그 결과를 쓴다.** 위에서 본 것처럼 값이 아니라 `Promise { <pending> }`이 들어온다. 화면에 `[object Promise]`가 찍히면 이 경우다.
- **`async` 함수 밖에서 `await`를 쓴다.** SyntaxError가 난다(모듈 최상위는 예외).
- **`try/catch`나 `.catch()`를 빠뜨린다.** 비동기 에러는 호출 스택이 이미 비워진 뒤에 발생하므로 바깥의 `try/catch`가 잡지 못하고 조용히 삼켜진다.
- **`.then()` 안에서 `return`을 빠뜨린다.** 다음 `.then()`이 앞의 완료를 기다리지 않아서 순서가 어긋난다. 체인을 쓸 거면 각 단계가 Promise를 반환해야 한다.
- **독립적인 호출을 순차 `await`로 쓴다.** 서로 결과를 참조하지 않는 세 개를 `await` 세 번으로 쓰면 걸리는 시간이 그대로 합산된다. 이럴 땐 `Promise.all()`로 한 번에 던지고 한 번만 기다린다. 반대로 앞의 결과를 뒤에서 써야 하면 순차 `await`가 맞다.

## 프로젝트 적용

[skala-front](https://github.com/hyun907/skala-front)에서 도시를 고르면 실시간 날씨를 가져오는 부분이 이 모델 그대로다.

```js
async function renderWeather(cityKey) {
  // 1) 기다리기 전에 로딩 상태를 먼저 그린다
  box.innerHTML = '<p class="weather-loading">로딩 중… ⏳</p>';

  try {
    // 2) 여기서 자리를 비켜준다. 화면은 계속 반응한다
    var data = await fetchWeather(city.lat, city.lon);
    box.innerHTML = /* 온도·습도로 교체 */;
  } catch (error) {
    // 3) 실패도 화면에 남긴다
    box.innerHTML = '<p class="weather-loading">⚠️ 날씨 정보를 가져오지 못했습니다.</p>';
  }
}
```

순서가 핵심이다. 로딩 표시를 `await` 앞에 그려야 사용자가 기다리는 동안 볼 게 있다. `await` 뒤에 그리면 데이터가 도착한 뒤라 띄울 이유가 없다. 그리고 `catch`가 없으면 실패했을 때 화면이 로딩 중에서 영원히 멈춘다.

LLM을 붙이면 같은 구조가 더 크게 걸린다. 응답이 몇 초씩 걸리므로 로딩 상태와 실패 경로는 선택이 아니고, 여러 문서를 임베딩하는 것처럼 서로 독립적인 호출은 `Promise.all()`로 묶어야 한다. 검색 후 생성처럼 앞 결과가 필요한 단계만 순차로 남긴다.

## 배운 점

나는 `await`를 그 줄에서 프로그램이 멈춰 서는 것으로 이해하고 있었다. 실행 순서를 찍어보니 멈추는 건 그 함수뿐이고, 그동안 다른 코드가 다 돌고 나서야 돌아온다. 그래서 이 모델의 결론이 데이터가 먼저 도착해도 끼어들 수 없다는 쪽으로 뒤집힌다.

이게 실제로 문제가 되는 지점도 같이 보인다. 사용자가 빠르게 두 번 요청하면 응답이 도착하는 순서는 보낸 순서와 무관하다. 먼저 보낸 요청이 늦게 도착해서 두 번째 답을 덮어쓸 수 있다는 뜻이고, 요청마다 식별자를 붙여 최신 것만 반영하는 처리는 이 실행 모델에서 나오는 요구사항이다. 순서를 보장해주는 장치가 언어에 없다는 걸 알고 나서야 그 코드를 왜 넣는지 알았다.
