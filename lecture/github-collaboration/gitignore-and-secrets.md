# .gitignore와 비밀정보 관리

## 개념 정의

`.gitignore`는 Git이 추적하지 않을 파일을 지정하는 파일이다. 비밀정보 관리는 API 키·토큰·비밀번호 같은 값이 저장소에 들어가지 않도록 하는 절차 전체를 말한다. 둘은 관련은 있지만 같은 것은 아니다.

## 동작 원리

Git은 모든 이력을 영구히 보존하도록 설계된 도구다. 이게 장점인데, 비밀값에 대해서는 정확히 그 장점이 문제가 된다.

```
비밀번호를 커밋 → 실수를 깨닫고 파일 삭제 → 다시 커밋
→ 파일은 지금 없지만, 이전 커밋에는 그대로 남아 있다
→ 저장소를 clone한 누구나 히스토리에서 꺼낼 수 있다
```

여기서 중요한 함정이 하나 있다: **`.gitignore`는 아직 Git이 추적하지 않는 파일에만 작동한다.** 이미 커밋된 파일을 나중에 `.gitignore`에 추가해도, Git은 계속 그 파일을 추적한다.

## 직접 확인한 예시

`.gitignore`가 이미 추적 중인 파일에는 소용없다는 주장을 실제로 재현해봤다.

```bash
# 1. .env를 먼저 커밋한다 (.gitignore 없는 상태)
echo "SECRET=1234" > .env
git add .env
git commit -m "실수로 .env 커밋"

# 2. 뒤늦게 .gitignore에 .env를 등록한다
echo ".env" > .gitignore

# 3. .env 내용을 바꿔본다
echo "SECRET=CHANGED" > .env
git status --short
```

결과:

```
 M .env
?? .gitignore
```

`.gitignore`에 등록했는데도 `.env`의 변경이 그대로 `M`(수정됨)으로 잡힌다. `.gitignore`는 이미 추적 중인 파일을 되돌아가서 무시해주지 않는다는 것이 확인됐다. 이미 커밋된 파일을 무시하려면 `git rm --cached 파일명`으로 추적 목록에서 먼저 빼야 한다.

## 자주 발생하는 오류

- **`git add .`로 `.env`가 딸려 들어간다.** `.gitignore`를 저장소 생성 직후, 코드를 쓰기 전에 먼저 만들어 두면 이 사고를 원천 차단할 수 있다.
- **`.gitignore`에 등록했으니 안전하다고 착각한다.** 위에서 확인했듯 이미 추적 중이면 소용없다. `git status`로 실제로 무시되고 있는지 확인하는 습관이 필요하다.
- **파일만 지우고 끝냈다고 착각한다.** 파일을 삭제해도 과거 커밋에는 그대로 남는다. 유출 대응은 삭제가 아니라 해당 키를 즉시 폐기하고 새로 발급하는 게 우선이다. 히스토리 정리는 그다음이다.

## 프로젝트 적용

LLM API 키처럼 유출되면 바로 금전 피해로 이어지는 값은 프론트엔드가 아니라 **백엔드에만** 둬야 한다. 프론트엔드 코드는 브라우저로 전부 전달되기 때문에, `.env`에 넣었다고 해도 클라이언트 번들에 포함되는 값이면 사실상 공개된 것과 같다. 팀 프로젝트에서는 저장소에 `.env.example`(값 없는 템플릿)만 올리고, 실제 값은 저장소 밖의 별도 채널로 공유하는 방식을 기본으로 삼고 있다.

## 배운 점

`.gitignore`를 쓰면 안전하다는 말에는 조건이 빠져 있었다. 이미 추적 중인 파일에는 통하지 않는다. `git status`에 `M .env`가 찍히는 걸 직접 보고 나서 저장소를 만들자마자 `.gitignore`부터 쓴다는 습관이 왜 순서상 중요한지 알았다. 나중에 추가하는 `.gitignore`는 이미 벌어진 일에는 손을 못 댄다.
