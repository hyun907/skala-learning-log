# 인덱스 설계: 만들었는데 안 쓰이는 게 정상일 때가 있다

## 개념 정의

인덱스는 **읽기를 사고 쓰기와 공간을 파는 거래**다.

| 얻는 것 | 내주는 것 |
|---|---|
| 조회가 `O(N)` → `O(log N)` | `INSERT`/`UPDATE`/`DELETE`마다 인덱스 재정렬 |
| | 인덱스 자체가 차지하는 디스크 |
| | 데이터가 쌓인 뒤 생성하면 **운영 중 부하** |

"인덱스를 걸면 빨라진다"까지만 알면 아무 데나 걸게 되고, 그러면 **조회는 그대로인데 쓰기만 느려진다.**

정확한 문장은 이쪽이다.

> **"인덱스가 있으면 빨라진다"가 아니라 "이 질문에 맞는 인덱스가 있어야 빨라진다."**

## 동작 원리

### 선택도가 낮으면 인덱스가 의미 없다

```
선택도 = 고유값 수 / 전체 행 수
```

| 컬럼 | 선택도 | 판정 |
|---|---|---|
| `email` | 1에 가깝다 | 좋다 |
| `gender` (M/F) | 0.5 | 나쁘다 |

`gender = 'M'`으로 인덱스를 타 봐야 절반이 나온다. **절반을 뽑을 거면 전체를 읽는 게 낫다.**

### 복합 인덱스는 선두 컬럼이 없으면 못 쓴다

`INDEX(customer_id, order_date DESC)`가 있을 때:

| 인덱스를 탄다 | 못 탄다 |
|---|---|
| `WHERE customer_id = 5` | `WHERE order_date > '2024-01-01'` |
| `WHERE customer_id = 5 AND order_date > ...` | (선두 컬럼 조건이 없다) |
| `WHERE customer_id = 5 ORDER BY order_date DESC` | |

전화번호부를 성으로 정렬해 뒀는데 이름만 알고 찾는 상황과 같다. **설계 규칙은 등호(`=`) 조건 컬럼을 먼저, 범위 조건을 나중에** 두는 것이다.

정렬 방향도 맞춰야 한다. `ORDER BY created_at DESC`를 자주 쓴다면 인덱스도 `DESC`로 만든다.

### 커버링 인덱스 — 테이블에 아예 안 간다

인덱스에는 보통 **키 값과 행의 위치**만 들어 있다. 그래서 `SELECT`할 컬럼이 인덱스에 없으면 위치를 따라 테이블(힙)로 한 번 더 가야 한다.

필요한 컬럼을 **인덱스 안에 다 넣어 두면** 그 왕복이 사라진다.

```sql
CREATE INDEX idx_email_cover ON users (email) INCLUDE (id, name);

EXPLAIN (ANALYZE, BUFFERS) SELECT id, name FROM users WHERE email = 'a@b.com';
--  Index Only Scan using idx_email_cover
--  Heap Fetches: 0        ← 테이블에 0번 접근
```

`Heap Fetches: 0`이 목표다. 그리고 **여기서 `SELECT *`가 왜 문제인지가 나온다.** 컬럼을 전부 요구하는 순간 커버링 인덱스가 무력화된다.

### 부분 인덱스 — 필요한 행만 색인한다

전체 행 중 일부만 조회 대상이라면 그 조건을 인덱스에 넣는다.

```sql
CREATE INDEX idx_orders_pending ON orders (created_at)
WHERE status = 'PENDING';
```

인덱스 크기가 줄어드니 탐색도 빨라지고 쓰기 부담도 준다.

## 직접 확인한 예시

이커머스 스키마에서 쿼리 11개를 튜닝하면서, 인덱스가 **통한 경우와 안 통한 경우를 둘 다** 만났다.

### 통한 경우 — 부분 인덱스로 Index Only Scan

"최근 1개월 실제 매출"을 구하는 쿼리였다. 유효한 주문 상태는 셋(`paid`, `shipped`, `delivered`)뿐이라 그 조건을 인덱스에 박았다.

```sql
CREATE INDEX idx_orders_sales_order_ts
    ON orders (order_ts, order_id)
 WHERE order_status IN ('paid', 'shipped', 'delivered');

ANALYZE orders;
```

컬럼 두 개를 넣은 이유가 명확하다. **`order_ts`는 기간 검색에 쓰고, `order_id`는 조인·집계에 쓴다.** 둘 다 인덱스에 있으면 힙에 갈 일이 없다.

| | 튜닝 전 | 튜닝 후 |
|---|---|---|
| 실행계획 | Seq Scan (5,284건 필터) | **Index Only Scan** |
| Heap Fetches | — | **0** |
| 실행시간 | 4.956 ms | 3.800 ms (−23.33%) |
| 버퍼 | 244 hit | 176 hit + **7 read** |

재미있는 건 버퍼다. **새로 만든 인덱스라 디스크에서 7페이지를 읽었는데도** 실행시간이 줄었다. 인덱스 효과가 그 비용을 넘었다는 뜻이다.

### 안 통한 경우 — 옵티마이저가 무시했다

재고가 임계치보다 낮은 상품을 찾는 쿼리에 부분 표현식 인덱스를 추가했다.

| | 튜닝 전 | 튜닝 후 |
|---|---|---|
| 실행계획 | Seq Scan + Hash Join | **완전히 동일** |
| 실행시간 | 0.211 ms | 0.208 ms |
| 버퍼 | 12 | 12 |

**옵티마이저가 새 인덱스를 아예 쓰지 않았다.**

처음엔 인덱스를 잘못 만들었나 싶었는데, 숫자를 보니 답이 나왔다. 대상 테이블이 **600행**이고 그중 **62행(약 10.3%)** 을 반환한다.

| 방식 | 실제로 하는 일 |
|---|---|
| Seq Scan | 페이지 몇 개를 **순차로** 읽는다. 테이블 전체가 버퍼 12개에 들어간다 |
| Index Scan | 인덱스를 읽고 → 매칭될 때마다 힙의 **랜덤 위치로 62번 점프** |

순차 읽기가 랜덤 읽기보다 훨씬 싸다. 게다가 인덱스 페이지와 힙 페이지를 **둘 다** 읽어야 한다. **전체의 10%를 넘게 읽는 쿼리에서는 Seq Scan이 정상적인 선택이다.**

즉 이건 **"인덱스를 잘못 만든 것"이 아니라 "인덱스가 필요 없는 상황이었던 것"** 이다. 0.003ms 차이는 측정오차 수준이라 개선이라고 부를 수도 없다.

### 그리고 더 큰 사실

11문항을 다 튜닝하고 나서 세어 보니 이랬다.

| | 문항 수 |
|---|---|
| 인덱스를 새로 만든 문항 | **2** |
| 그중 실제로 쓰인 것 | **1** |
| 쿼리 구조 변경으로 해결한 문항 | **9** |

**"느리면 인덱스"는 반사적으로 나오는 답인데, 실측에서는 1/11이었다.**

## 자주 발생하는 오류

**인덱스를 만들고 확인하지 않는다**

만든 것과 쓰이는 것은 다르다. 추가 후에는 반드시 `EXPLAIN`으로 실행계획을 본다.

**대상 행 비율을 계산하지 않는다**

10%를 넘으면 효과를 기대하기 어렵다. 만들기 전에 `COUNT`로 먼저 재 보면 시간을 아낀다.

**안 쓰이는 인덱스를 방치한다**

조회 이득 없이 쓰기 비용과 저장 공간만 낸다. PostgreSQL은 이렇게 찾는다.

```sql
SELECT indexrelname, relname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

**외래키에 인덱스가 없다**

PostgreSQL은 기본키에는 인덱스를 자동 생성하지만 **외래키에는 만들어 주지 않는다.** 조인할 때마다 전체 스캔이 되고, 부모 행을 지울 때 자식을 찾는 것도 전체 스캔이 된다.

**데이터가 쌓인 뒤 운영 중에 만든다**

인덱스 생성은 조용한 작업이 아니다. 특히 데이터를 물리적으로 재정렬하는 종류의 인덱스는 그 시간 동안 다른 트랜잭션을 막는다. PostgreSQL에는 잠금을 줄이는 옵션이 있다.

```sql
CREATE INDEX CONCURRENTLY idx_products_category ON products (category_id);
```

## 프로젝트 적용

**개인정보 컬럼에는 인덱스를 걸기 어렵다.**

주민번호나 이메일처럼 암호화해야 하는 컬럼은 인덱싱하려면 "복호화 → 색인 → 재암호화" 문제가 생긴다. 실무에서는 **순차 증가하는 시스템 ID를 따로 두고 그걸 인덱싱한다.**

이건 "개인정보를 기본키로 쓰지 말라"는 설계 원칙과 같은 결론에 **다른 이유로** 도달한다. 무결성 때문이 아니라 성능 때문이다.

**로그성 테이블은 인덱스를 최소화한다.**

쓰기 빈도가 높은 테이블에 인덱스를 여러 개 걸면 **`INSERT`마다 그만큼 재정렬**이 일어난다. 조회는 정렬로 처리하고, 분석이 필요하면 운영 DB가 아니라 별도 분석 영역에서 한다.

**작은 테이블은 튜닝 대상이 아니다.**

0.2ms짜리 쿼리를 고치는 시간에 28ms짜리를 보는 게 낫다. 어떤 쿼리를 볼지 고르는 것도 튜닝의 일부다.

## 배운 점

**"고쳤는데 아무 일도 안 일어났다"는 세 가지 중 하나다.**

| 상황 | 무엇인가 | 어떻게 구분하나 |
|---|---|---|
| 잘못 고쳤다 | 인덱스 정의가 조건과 안 맞는다 | 실행계획도 안 바뀌고 이유도 설명이 안 된다 |
| **고칠 필요가 없었다** | 원래 문제가 아니었다 | **실행계획이 안 바뀌었다 = 옵티마이저가 안 골랐다** |
| 측정이 부족하다 | 차이가 있는데 한 번 재서는 안 보인다 | 실행계획은 바뀌었는데 시간이 그대로다 |

셋을 구분하지 못하면 두 번째를 첫 번째로 착각하고 **계속 인덱스를 늘린다.** 그러면 조회는 안 빨라지고 쓰기만 느려진다.

**그리고 이건 AI에게 SQL 튜닝을 물을 때 특히 조심할 지점이다.** LLM은 스키마를 봐도 **데이터가 몇 건인지, 값이 어떻게 분포하는지를 모른다.** "인덱스를 추가하세요"는 언제나 그럴듯하게 들리지만, 내 실습에서 그건 11번 중 1번만 맞는 답이었다.
