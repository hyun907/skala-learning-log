# JOIN 알고리즘: INNER/LEFT는 의미고, Hash/Nested Loop는 실행이다

## 개념 정의

`JOIN`이라는 단어가 두 가지 다른 것을 가리킨다. 이걸 섞으면 "왜 이 조인이 느리지"에 답할 수 없다.

| | 무엇을 정하나 | 종류 |
|---|---|---|
| **JOIN 종류** | **의미** — 매칭 안 된 행을 어떻게 할 것인가 | `INNER`, `LEFT`, `RIGHT`, `FULL` |
| **JOIN 알고리즘** | **실행** — 행을 실제로 어떻게 결합할 것인가 | Nested Loop, Hash, Merge |

**둘은 독립이다.** `LEFT JOIN`도 Hash로 실행될 수 있고, `INNER JOIN`도 Nested Loop으로 실행될 수 있다. 내가 SQL에 쓰는 건 앞쪽뿐이고, **뒤쪽은 옵티마이저가 고른다.**

논리적으로 `A JOIN B ON 조건`은 **A와 B의 모든 조합을 만든 뒤 조건에 맞는 것만 남기는 것**이다. 하지만 100만 × 100만을 실제로 만들면 어떤 DB도 죽는다. 그래서 곱을 만들지 않고 우회하는 방법이 셋 있다.

## 동작 원리

### Nested Loop — 작은 쪽이 큰 쪽을 훑는다

```
바깥 테이블의 각 행마다:
    안쪽 테이블에서 조건에 맞는 행을 찾는다
```

바깥이 N행이면 안쪽 탐색이 N번 일어난다. 그래서 두 조건이 **동시에** 필요하다.

1. **바깥이 작아야** 한다
2. **안쪽에 인덱스가 있어야** 한다 (매 탐색이 즉시 끝나야 하므로)

둘 중 하나만 어긋나도 급격히 느려진다. 전형적인 사용처는 **큰 테이블 × 작은 코드 테이블**이다. 사용자 목록에 등급 코드 테이블을 붙이는 식.

### Hash Join — 곱을 해시 조회로 바꾼다

작은 쪽 전체를 메모리에 해시 테이블로 올리고(Build), 큰 쪽을 한 번 흘려보내며 해시로 찾는다(Probe). **양쪽을 한 번씩만 읽으면 끝난다.**

대신 **메모리**가 필요하다. 작은 쪽이 메모리에 안 들어가면 디스크로 쪼개서 처리하고, 그 순간 느려진다. PostgreSQL 실행계획에서 `Batches`가 1보다 크면 그 상황이다.

인덱스가 없어도 되고 대량 데이터에 강하다. 다만 **등가 조인(`=`)에만** 쓸 수 있다.

### Merge Join — 정렬해 두고 나란히 훑는다

양쪽을 조인 키로 정렬한 뒤 두 포인터로 동시에 전진한다. 정렬이 비싸지만 **이미 정렬돼 있으면 공짜**고, `=`이 아닌 **범위 조건에도 쓸 수 있다.**

### 정리

| 알고리즘 | 유리한 상황 | 주의 |
|---|---|---|
| **Nested Loop** | 바깥이 작고 + 안쪽에 인덱스 | 바깥이 크면 반복 폭발 |
| **Hash** | 대량 등가 조인, 인덱스 없어도 됨 | 메모리 부족 시 디스크 |
| **Merge** | 이미 정렬됨, 범위 조인 | 정렬을 새로 하면 초기 비용 |

## 직접 확인한 예시

이커머스 스키마의 쿼리 11개를 튜닝하면서 **셋을 전부 실행계획에서 봤다.** 각각 왜 선택됐는지가 명확했다.

### Hash Join — 가장 많이 나타났다

주문 테이블과 주문상품 테이블을 붙이는 조인은 거의 항상 Hash Join이었다.

이유가 단순하다. **수천~수만 행의 등가 조인**이고, 정렬돼 있지 않으며, 양쪽 다 크다. 이 조건이면 Hash가 맞다.

처음에는 "인덱스를 걸었는데 왜 Hash지"라고 생각했는데, 그게 아니었다. **비용 기반 선택이 그렇게 나온 것이고, 그 판단이 옳았다.** 인덱스를 타고 수천 번 랜덤 접근하는 것보다 한 번씩 흘려보내는 게 싸다.

### Nested Loop — 이름이 문제가 아니라 반복 횟수가 문제였다

재구매율 쿼리에서 Nested Loop이 문제로 나타났다. 그런데 **Nested Loop 자체가 나쁜 게 아니었다.**

문제는 상관 서브쿼리가 **고객 2,084명마다 반복**되고 있었다는 것이다. 실행계획에서 `loops` 값이 그만큼 크게 찍힌다.

윈도우 함수로 바꿔서 반복을 없앴더니:

| | 튜닝 전 | 튜닝 후 |
|---|---|---|
| 구조 | 고객별 반복 Index Scan | 한 번의 정렬 + WindowAgg |
| **버퍼** | **12,594** | **90** |
| 실행시간 | 8.377 ms | 5.263 ms |

같은 쿼리에서 파라미터 1행과 결합하는 Nested Loop도 있었는데, 그건 비용이 사실상 0이었다. **1행 × N번은 문제가 아니고 2,084행 × N번이 문제다.**

### Merge Join — 항상 나쁜 것도 아니었다

카테고리별 매출 Top 10 쿼리의 튜닝 전 계획에 Merge Join이 있었다.

여기서 비쌌던 이유는 Merge Join이라서가 아니라, **카테고리 경로 문자열을 10,735건의 판매 데이터와 일찍 결합했기** 때문이다. 넓어진 결과를 정렬하고 집계하니 비용이 커졌다.

숫자 ID로 먼저 집계하고 **상위 결과에만 경로 문자열을 붙이는** 순서로 바꾸자 22.465 ms → 14.917 ms(−33.60%)가 됐다. 조인 방식을 강제로 바꾼 게 아니라 **입력을 줄이니 옵티마이저의 선택도 달라졌다.**

## 자주 발생하는 오류

**`ON` 절을 빼먹는다**

조인 조건이 없으면 카르테시안 곱이 된다. 양쪽 100만 건이면 1조 행이다. 테이블 5개를 조인하면 `ON` 조건이 4개 필요한데, **하나라도 빠지면 그 테이블은 전체 스캔**이 된다.

**외래키에 인덱스가 없다**

PostgreSQL은 기본키에만 인덱스를 자동 생성한다. 외래키 컬럼에 인덱스가 없으면 Nested Loop이 성립할 수 없고, 옵티마이저는 어쩔 수 없이 Hash나 Seq Scan을 고른다.

**통계가 낡아서 오판한다**

옵티마이저는 "이 조건이면 몇 행쯤 나오겠다"는 추정으로 알고리즘을 고른다. 추정이 틀리면 **큰 테이블을 작은 테이블처럼 취급하는** 계획이 나온다. `ANALYZE`로 갱신한다.

**메모리를 늘려서 해결하려 한다**

Hash Join이 디스크를 쓴다고 `work_mem`을 키우면 그 세션은 빨라지지만, **같은 머신의 다른 프로세스가 쓸 메모리가 줄어든다.** 자원은 제로섬이다.

**조인 개수가 너무 많다**

테이블 4~5개를 조인해서 결국 한 행을 얻는다면, 그건 조인 문제가 아니라 **설계 문제**일 수 있다. 조회 전용 영역이라면 테이블을 합치는 것도 선택지다.

## 프로젝트 적용

**느려진 조회 API를 진단하는 첫 단계로 쓴다.**

`EXPLAIN (ANALYZE, BUFFERS)`를 찍고 이 순서로 본다.

1. **어떤 알고리즘인가** — Hash인지 Nested Loop인지
2. **`loops`가 큰가** — 크면 반복이 있다는 뜻이고, 대개 서브쿼리 구조 문제다
3. **큰 테이블에 `Seq Scan`이 있는가** — 인덱스 후보
4. **예상 `rows`와 실제가 벌어지는가** — 통계 갱신 필요

**AI가 생성한 SQL을 검토할 때도 같다.** LLM은 문법이 맞는 조인을 잘 만들지만 **인덱스가 있는지, 데이터가 몇 건인지를 모른다.** 그래서 생성된 쿼리는 실행계획으로 확인해야 하고, 이때 알고리즘을 읽을 줄 알아야 무엇이 문제인지 말할 수 있다.

## 배운 점

**"이 조인 왜 느려요"에 답하려면 두 층을 나눠서 봐야 한다.**

`INNER JOIN`을 `LEFT JOIN`으로 바꾸는 건 **결과의 의미**를 바꾸는 일이지 성능 튜닝이 아니다. 반대로 성능이 문제라면 고칠 것은 문법이 아니라 **입력 크기, 인덱스, 통계** 셋 중 하나다.

내 실습에서 조인 성능이 개선된 문항들은 전부 **조인 문법을 안 건드렸다.** 대신 조인에 들어가는 입력을 줄였다 — 미리 집계하거나, 상세 테이블 결합을 뒤로 미루거나.

**옵티마이저를 이기려 하지 말고 조건을 만들어 주는 쪽이 낫다.** 인덱스를 만들고, 통계를 갱신하고, 입력을 줄이면 알고리즘 선택은 알아서 좋아진다.
