# 실행계획 읽기: 실행시간만 보면 반대로 판단한다

## 개념 정의

`EXPLAIN`은 DB에게 **"이 쿼리를 어떻게 실행할 작정이냐"** 를 물어보는 명령이다.

SQL은 선언형이다. `SELECT`는 *무엇을* 원하는지만 적고, *어떻게* 가져올지는 옵티마이저가 정한다. 그래서 **같은 SQL이 데이터 크기와 인덱스 상태에 따라 완전히 다른 방식으로 실행된다.** 쿼리를 짜는 것과 쿼리가 빠른 것은 별개이고, 그 사이를 잇는 유일한 도구가 실행계획이다.

세 가지 형태가 있고 성격이 다르다.

| 명령 | 실행하나 | 얻는 것 |
|---|---|---|
| `EXPLAIN` | 안 함 | 옵티마이저의 **예상** 계획 |
| `EXPLAIN ANALYZE` | **실제로 실행** | 예상 + **실측 시간·행 수** |
| `EXPLAIN (ANALYZE, BUFFERS)` | 실제로 실행 | 위 + **읽은 페이지 수** |

`ANALYZE`가 붙으면 쿼리가 진짜로 돈다. `UPDATE`나 `DELETE`에 쓰면 데이터가 실제로 바뀌므로 트랜잭션으로 감싸야 한다.

```sql
BEGIN;
EXPLAIN ANALYZE UPDATE orders SET status = 'DONE' WHERE id = 1;
ROLLBACK;
```

## 동작 원리

실행계획은 트리다. **안쪽에서 바깥으로, 깊이 들여쓰기된 것부터** 실행된다.

```
Hash Join  (cost=12.5..45.8 rows=200 width=32)
           (actual time=0.5..2.3 rows=185 loops=1)
  Hash Cond: (e.student_id = s.id)
  Buffers: shared hit=12 read=5
  ->  Seq Scan on enrollments
  ->  Hash
        ->  Index Scan on students
              Index Cond: (major_id = 1)
```

읽을 때 보는 값이 넷이다.

**① 어떤 노드인가**

| 노드 | 뜻 | 판정 |
|---|---|---|
| `Seq Scan` | 테이블 전체를 순서대로 읽는다 | 큰 테이블이면 검토 대상 |
| `Index Scan` | 인덱스로 위치를 찾고 테이블에 접근 | 좋다 |
| `Index Only Scan` | **인덱스만으로 끝. 테이블에 안 간다** | 가장 좋다 |
| `Sort` | 결과를 정렬한다 | 정렬 컬럼에 인덱스가 없다는 신호 |
| `Hash Join` / `Nested Loop` / `Merge Join` | 조인을 실제로 수행하는 방식 | 상황에 따라 다름 |

**② `rows` 예상값과 `actual rows`의 차이**

옵티마이저는 테이블 통계를 보고 "이 조건이면 200행쯤 나오겠다"고 추정한 뒤, 그 추정에 맞는 실행 방식을 고른다. **추정이 틀리면 선택도 틀린다.**

예상과 실제가 몇 배 이상 벌어지면 통계가 낡은 것이다. `ANALYZE 테이블명;`으로 갱신한다.

**③ `Buffers`**

`hit`은 메모리에서 찾은 페이지, `read`는 디스크에서 읽은 페이지다. **`read`가 많다는 건 메모리로 감당이 안 됐다는 뜻**이고, 그만큼 느려진다.

**④ `loops`**

이 노드가 몇 번 반복됐는지다. `loops=2084`처럼 큰 숫자가 보이면 **바깥 행마다 안쪽을 다시 돌고 있다**는 뜻이라 거의 항상 문제다.

## 직접 확인한 예시

이커머스 스키마에서 쿼리 11개를 튜닝하면서 전부 `EXPLAIN (ANALYZE, BUFFERS)`로 전후를 쟀다. 그러면서 **실행시간만 보면 안 되는 이유**를 두 번 만났다.

### 사례 1 — 시간은 줄었는데 버퍼가 늘었다

고객 RFM 분석 쿼리를 선집계 구조로 바꿨다.

| | 튜닝 전 | 튜닝 후 |
|---|---|---|
| 실행시간 | 28.991 ms | 26.870 ms (**−7.32%**) |
| **버퍼** | 284 | **305 (증가)** |

실행시간만 보면 "7.32% 개선"이다. 그런데 **읽은 페이지가 늘었다.** 일을 덜 했는데 시간이 줄었다면 개선이지만, **더 읽고도 조금 빨라진 것**은 개선이라고 부르기 어렵다. 단일 실행값이라 캐시 상태 차이일 가능성도 있다.

그래서 이 문항은 **"개선"이 아니라 "판정 유보, 반복 측정 필요"** 로 적었다. 실행시간 하나만 봤으면 그냥 성공으로 기록했을 것이다.

### 사례 2 — 아무것도 안 바뀌었는데 그게 정답이었다

재고 임계치 탐지 쿼리에 인덱스를 추가했다.

| | 튜닝 전 | 튜닝 후 |
|---|---|---|
| 실행계획 | Seq Scan + Hash Join | **완전히 동일** |
| 실행시간 | 0.211 ms | 0.208 ms |
| 버퍼 | 12 | 12 |

**옵티마이저가 새 인덱스를 아예 쓰지 않았다.** 대상 테이블이 600행이고 그중 62행(약 10%)을 반환하는 쿼리인데, 이 정도 비율이면 인덱스를 타고 힙을 62번 오가는 것보다 **600행을 통째로 읽는 게 더 싸다.**

여기서 판단이 갈린다. 실행계획을 안 봤다면 "인덱스를 걸었는데 왜 안 빨라지지"에서 멈췄을 것이다. **실행계획이 안 바뀐 걸 확인했기 때문에 "인덱스가 안 쓰인 것"과 "인덱스가 쓰였는데 효과가 없는 것"을 구분할 수 있었다.**

### 사례 3 — 반복 실행이 보이면 거의 항상 문제다

첫 구매 후 30일 재구매율 쿼리는 고객마다 서브쿼리가 반복 실행되고 있었다.

| | 튜닝 전 | 튜닝 후 |
|---|---|---|
| **버퍼** | **12,594** | **90** |
| 실행시간 | 8.377 ms | 5.263 ms |

**버퍼가 140분의 1이 됐다.** 실행시간은 37% 줄었을 뿐인데 실제로 읽은 페이지는 자릿수가 달라졌다. 데이터가 지금보다 커지면 이 격차가 그대로 시간 차이로 나타난다.

**실행시간 −37%와 버퍼 −99.3% 중에서, 미래를 예측하는 쪽은 버퍼다.**

## 자주 발생하는 오류

**`EXPLAIN ANALYZE`로 DML을 그냥 실행한다**

`ANALYZE`는 실제로 실행한다. 트랜잭션 없이 `UPDATE`에 붙이면 데이터가 바뀐다.

**한 번 재고 결론을 낸다**

캐시가 따뜻한지 차가운지에 따라 같은 쿼리가 몇 배 차이 난다. 내가 잰 11문항도 전부 단일 실행값이라, 차이가 작은 문항(−7.32%, −1.42%)은 사실상 아무것도 증명하지 못한다. **최소 4~5회 실행해서 중앙값으로 봐야 한다.**

**인덱스가 안 보인다고 실패로 판단한다**

전체 행의 10%를 넘게 읽는 쿼리라면 `Seq Scan`이 정상이다. 옵티마이저가 비용을 계산해서 고른 결과다.

**통계가 낡은 걸 눈치채지 못한다**

예상 `rows`와 `actual rows`가 크게 다르면 옵티마이저가 잘못된 전제로 계획을 세운 것이다. 쿼리를 고치기 전에 `ANALYZE`부터 돌려야 한다.

## 프로젝트 적용

**AI가 생성한 SQL을 검증하는 도구로 쓴다.**

LLM에게 쿼리를 짜 달라고 하면 문법적으로 맞는 결과가 잘 나온다. 그런데 LLM은 **그 테이블에 인덱스가 뭐가 있는지, 데이터가 몇 건인지, 값의 분포가 어떤지를 모른다.** 스키마를 줘도 모른다.

내 실습에서 이게 실제로 갈렸다. "느리면 인덱스를 추가하라"는 가장 흔한 조언인데, **11문항 중 인덱스가 답이었던 건 1문항뿐이고 나머지 하나는 만들었는데 쓰이지도 않았다.** 실제로 통한 건 쿼리 구조 변경이었다.

그래서 생성된 SQL을 받으면 절차가 이렇게 된다.

1. 결과가 맞는지 확인한다
2. `EXPLAIN (ANALYZE, BUFFERS)`로 실행계획을 본다
3. `Seq Scan`이 큰 테이블에 있는지, `loops`가 큰지, 예상/실제 행 수가 벌어지는지 본다
4. 고치고 **다시 잰다**

코드 리뷰에서 "이 코드가 돌아가나"와 "이 코드가 괜찮나"를 다르게 보는 것과 같다. SQL에서는 후자가 `EXPLAIN`이다.

## 배운 점

**측정값 하나로는 방향도 못 정한다.**

세 사례 전부에서 판단을 바꾼 건 실행시간이 아니었다.

| 사례 | 실행시간이 말한 것 | 실제 판단 근거 |
|---|---|---|
| RFM | "7.32% 개선" | **버퍼 증가** → 유보 |
| 재고 탐지 | "1.42% 개선" | **실행계획 무변화** → 정상 동작 |
| 재구매율 | "37% 개선" | **버퍼 140분의 1** → 규모가 커지면 더 벌어진다 |

지표를 하나만 보면 두 방향으로 틀린다. 좋아 보이는데 아닐 수도 있고, 그대로인데 문제가 없을 수도 있다.

**그리고 실행계획은 성능 도구이기 전에 커뮤니케이션 도구다.** "이 쿼리 느린데요"는 논쟁이 되지만, 실행계획을 캡처해서 "여기서 `Seq Scan`이 13,837행을 훑고 있습니다"는 논쟁이 안 된다. 숫자가 대신 말한다.
