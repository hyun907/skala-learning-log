# GitHub Pages에 SPA 배포하기: 화면이 정상이어도 404가 온다

## 개념 정의

Vue Router를 history 모드로 쓰면 주소가 `/weather/seoul` 같은 평범한 경로가 된다. 앱 안에서 링크를 눌러 이동할 때는 네트워크 요청이 아예 발생하지 않는다. 브라우저 히스토리만 바꾸고 화면을 갈아 끼우기 때문이다.

문제는 그 주소로 **직접** 들어올 때다.

```
링크 클릭     /weather/seoul  →  라우터가 처리        →  정상
새로고침(F5)  /weather/seoul  →  서버에 GET 요청      →  그런 파일이 없다
링크 공유     (남이 그 주소로 접속)                   →  그런 파일이 없다
```

서버 입장에서 `/weather/seoul`은 그냥 존재하지 않는 경로다. 그런 파일이 디스크에 없으니 404를 준다.

일반적인 해법은 서버 설정이다. "어떤 경로로 들어와도 `index.html`을 돌려줘라"를 Nginx의 `try_files`나 Netlify의 `_redirects`로 지시한다. 그러면 서버가 200과 함께 앱을 주고, 앱이 부팅한 뒤 주소를 읽어 알아서 라우팅한다.

**GitHub Pages에는 그 설정이 없다.** 정적 파일을 그대로 내려줄 뿐이고 rewrite 규칙을 줄 수 없다. 그래서 여기서는 우회로를 써야 한다.

## 동작 원리

우회로는 세 가지가 있고, 나는 세 저장소에서 각각 다른 걸 썼다.

### 방법 1. 해시 라우팅

```js
const router = createRouter({
  history: createWebHashHistory(),   // /#/weather/seoul
  routes: [...]
})
```

`#` 뒤의 문자열은 **브라우저가 서버에 보내지 않는다.** 서버가 받는 요청은 언제나 루트 하나뿐이고, 루트에는 `index.html`이 실제로 있다. 그래서 404가 원천적으로 발생하지 않는다.

한 줄로 끝나지만 주소에 `#`이 박힌다. 그리고 크롤러는 `#` 뒤를 무시하므로 검색 노출이 사실상 죽는다.

### 방법 2. `404.html` 리다이렉트 트릭

GitHub Pages는 없는 경로에 대해 저장소에 `404.html`이 있으면 그걸 돌려준다. 이 성질을 이용한다. `404.html`에 스크립트를 심어 원래 경로를 쿼리스트링으로 인코딩한 뒤 루트로 넘기고, 루트에서 `history.replaceState`로 주소를 복원한다.

```html
<!-- public/404.html -->
<script>
  var pathSegmentsToKeep = 1   // 프로젝트 페이지라 /저장소이름/ 한 칸은 남긴다
  var l = window.location
  l.replace(/* 경로를 ?/ 뒤로 접어 넣어 루트로 보낸다 */)
</script>
```

주소는 깨끗해지지만 리다이렉트가 한 번 왕복하고, `pathSegmentsToKeep`이라는 **손으로 맞춰야 하는 숫자**가 생긴다.

### 방법 3. 빌드 후 `index.html`을 `404.html`로 복사

```js
// vite.config.js
{
  name: 'spa-fallback',
  closeBundle() {
    copyFileSync(resolve(root, outDir, 'index.html'),
                 resolve(root, outDir, '404.html'))
  }
}
```

발상이 단순하다. 어차피 없는 경로면 GitHub Pages가 `404.html`을 준다. **그 내용을 `index.html`과 똑같이 만들어 두면** 무슨 경로로 들어오든 앱이 뜬다. 리다이렉트도 없고 주소 조작도 없다.

## 직접 확인한 예시

세 방식을 브라우저로 열어보면 **셋 다 똑같이 잘 된다.** 차이가 눈에 안 보인다. 그래서 배포본에 직접 요청을 보내 상태 코드와 응답 본문을 확인했다.

```bash
curl -s -o /dev/null -w "%{http_code} %{size_download}\n" \
  https://hyun907.github.io/vue-project/weather/seoul
```

| 요청 | 1. 해시 | 2. 리다이렉트 트릭 | 3. 복사 |
|---|---|---|---|
| `/` | `200` · 앱 | `200` · 앱 | `200` · 앱 |
| 없는 깊은 경로 | `404` · GitHub 기본 404 페이지 (9,379B) | `404` · 리다이렉트 스크립트 (1,015B) | `404` · **앱** (774B) |
| `/404.html` | `404` · 기본 페이지 (파일 없음) | `200` · 리다이렉트 스크립트 | `200` · 앱 |

여기서 세 가지를 알게 됐다.

**첫째, 방법 3은 404를 없애는 게 아니라 404와 함께 앱을 준다.** `/weather/seoul`은 여전히 `404` 상태 코드로 돌아온다. 본문이 앱이라 사용자 눈에는 완벽히 정상이지만, HTTP 계층에서는 실패로 기록된다. Nginx `try_files`가 `200`을 주는 것과는 다른 물건이다. 크롤러와 업타임 모니터링은 상태 코드를 보므로, 이걸 오류로 셀 수 있다.

**둘째, 복사가 실제로 일어났는지도 확인됐다.** `index.html`과 `404.html`을 각각 내려받아 비교하니 **774바이트가 바이트 단위로 완전히 동일**했다. 5줄짜리 빌드 플러그인이 배포 산출물까지 반영된 것을 눈이 아니라 파일로 확인한 셈이다.

```bash
cmp index.html 404.html && echo "동일"
```

**셋째, 방법 1에만 있는 장점을 뒤늦게 발견했다.** 해시 라우팅은 없는 경로에서 GitHub의 기본 404 페이지를 그대로 받는다. **진짜 404를 보여줄 수 있는 유일한 방법이다.** 방법 2와 3은 없는 경로를 전부 앱으로 삼켜버려서, 오타로 들어온 주소든 삭제된 페이지든 구분 없이 앱이 뜬다.

처음 세 방식을 비교할 때 나는 URL 모양, 코드량, 이전 용이성만 표에 적었다. **"없는 페이지를 없다고 말할 수 있는가"라는 축이 통째로 빠져 있었고**, 그건 실제로 요청을 보내보기 전까지 떠오르지 않았다.

## 자주 발생하는 오류

**`pathSegmentsToKeep`을 안 고쳐서 조용히 깨진다.** 방법 2의 이 숫자는 "저장소 이름 몇 칸을 남길 것인가"를 뜻한다. 저장소 이름을 바꾸거나 사용자 페이지(`계정.github.io`)로 옮기면 값이 달라지는데, 안 고쳐도 에러가 안 난다. 그냥 엉뚱한 곳으로 리다이렉트될 뿐이다.

**`base` 설정을 빠뜨려 자산 경로가 깨진다.** 프로젝트 페이지는 `/저장소이름/` 아래에 배포되므로 Vite의 `base`를 맞춰야 한다. 안 맞으면 앱은 뜨는데 CSS와 JS가 404가 난다. 나는 이 값을 환경변수로 빼서 CI에서 주입했다 — [Vite 환경변수와 빌드 모드](vite-env-and-build-modes.md)에 정리해 두었다.

**catch-all 라우트를 `redirect`로 처리하면 404 화면이 사라진다.** 세 저장소 모두 잘못된 경로를 홈으로 리다이렉트하게 짜뒀는데, 그 결과 404 화면 자체가 존재하지 않게 됐다. 방법 3을 쓰면 어차피 서버가 404를 구분해주지 않으므로, **404 화면은 앱이 직접 만들어야 한다.**

## 프로젝트 적용

최종 프로젝트에는 방법 3을 남겼다. 결정적인 이유는 코드량이나 URL 모양이 아니라 **손으로 맞춰야 하는 설정값이 없다**는 점이었다. 방법 2의 `pathSegmentsToKeep`은 저장소 이름에 묶여 있어서, 이름을 바꾸는 순간 조용히 깨진다. 방법 3에는 그런 값이 아예 없다.

되돌리기 쉬운 것도 컸다. 나중에 Netlify나 Vercel로 옮기면 `404.html`은 그냥 무시되는 파일이 된다. 지우지 않아도 해가 없다.

반면 학습용으로 만든 실습 저장소에는 방법 1을 그대로 뒀다. 9개 실습 단계를 라우트로 나눈 인덱스라서 **검색에 걸릴 이유가 없고**, 단계가 계속 늘어나는데 배포 설정을 매번 신경 쓰고 싶지 않았다. 같은 문제라도 "검색되어야 하는 서비스"와 "내가 보려고 만든 인덱스"의 답이 달랐다.

이 결정은 **서버를 둘 수 없다는 제약 위에서만 유효하다.** 백엔드가 생기는 순간 `try_files` 한 줄이 정답이 되고 세 방법 모두 필요 없어진다. 검색 노출이 필요해지면 세 방법 다 부족하고 SSR로 가야 한다.

## 배운 점

**같은 문제를 세 번 다르게 푼 것이 비교의 근거가 됐다.** 한 번만 풀었으면 "이렇게 하면 된다"밖에 못 썼을 것이다. 세 번 풀었기 때문에 각 방법이 무엇을 대가로 지불하는지 말할 수 있게 됐고, 다음에 같은 상황을 만나면 조건을 보고 즉시 고를 수 있다.

**그리고 "배포가 됐다"와 "배포가 옳게 됐다"는 다른 질문이었다.** 브라우저로 열어보는 것은 전자만 답한다. 화면이 뜨면 성공처럼 보이니까. 후자는 상태 코드와 응답 크기를 봐야 나오고, 실제로 그렇게 보고 나서야 방법 3이 404를 없앤 게 아니라 404 위에 앱을 얹은 것이라는 걸 알았다.

눈으로 확인할 수 있는 층과 실제로 계약이 맺어지는 층이 다를 때, 확인은 후자에서 해야 한다.
