# macOS 개발 환경: source가 왜 필요한가

## 개념 정의

새 도구를 설치한 직후 터미널에서 `command not found`가 뜨는 경우가 있다. 대부분 도구가 잘못 설치된 게 아니라, **지금 열려 있는 셸 세션이 아직 새 설정을 모르기 때문**이다. `source ~/.zshrc`가 이 문제를 해결하는데, 이게 왜 필요한지는 셸이 설정 파일을 언제 읽는지를 알아야 이해된다.

## 동작 원리

`.zshrc`, `.zprofile` 같은 셸 설정 파일은 **새 셸 세션이 시작될 때** 읽힌다. 이미 실행 중인 터미널 세션은 그 시점 이후로 파일 내용을 다시 읽지 않는다. Homebrew 같은 설치 스크립트가 PATH를 `.zshrc`에 추가해도, 그건 파일에 적어 둔 것일 뿐 지금 열려 있는 터미널의 환경변수에 즉시 반영되지 않는다.

`source 파일명`은 그 파일에 적힌 명령어를 **지금 이 셸에서 직접 실행**한다. 그래서 `source ~/.zshrc`를 실행하면 파일에 적힌 `export PATH=...`가 현재 세션에도 적용된다. 새 터미널 창을 여는 것도 같은 효과다 — 새 세션이 시작되면서 파일을 다시 읽기 때문이다.

## 직접 확인한 예시

PATH에 없는 실행 파일을 만들어 놓고, 파일에만 PATH를 추가했을 때와 현재 셸에 직접 반영했을 때를 비교했다.

```bash
# 실행 파일 준비
mkdir -p ~/path-test/bin
cat > ~/path-test/bin/mytool << 'EOF'
#!/bin/bash
echo "mytool 실행됨"
EOF
chmod +x ~/path-test/bin/mytool

# 1. 아직 PATH에 없는 상태
mytool
# command not found: mytool

# 2. .zshrc 파일에만 PATH를 추가 (source 안 함)
echo 'export PATH="$HOME/path-test/bin:$PATH"' >> ~/.zshrc
mytool
# 여전히 command not found: mytool  ← 파일에 적었을 뿐 현재 셸엔 반영 안 됨

# 3. 현재 셸에 직접 반영 (source ~/.zshrc와 동일한 효과)
export PATH="$HOME/path-test/bin:$PATH"
mytool
# mytool 실행됨
```

파일을 수정한 시점과 현재 셸에 반영되는 시점이 다르다는 게 명확히 확인됐다. `.zshrc`에 PATH를 추가하는 것과, 그걸 지금 세션에 적용하는 것은 별개의 단계다.

## 자주 발생하는 오류

- **`permission denied`로 설치 스크립트가 안 돌아간다.** 실행 권한이 없는 경우다. `chmod +x 스크립트명`으로 실행 권한을 부여하면 해결된다.
- **분명 설치했는데 `command not found`가 뜬다.** 위에서 확인한 것처럼 새 PATH가 현재 셸에 아직 반영 안 된 경우가 많다. `source ~/.zshrc`를 실행하거나 터미널을 새로 열면 해결된다.
- **Docker 관련 명령어가 `command not found`로 뜬다.** Docker CLI는 설치돼 있어도 Docker Desktop 앱이 실행 중이 아니면 데몬에 연결이 안 된다. 앱을 먼저 켜야 한다.

## 프로젝트 적용

새 팀원 온보딩 문서에 으레 들어가는 설치 후 터미널을 재시작하라는 한 줄이 왜 필요한지 이 원리로 설명할 수 있다. 그냥 재시작하면 된다고만 알려주는 것보다, 지금 세션은 그 시점 이후의 설정 변경을 모른다는 이유까지 알려주면, 비슷한 문제(예: 환경 변수를 바꿨는데 프로그램이 옛날 값을 쓰는 문제)를 만났을 때도 같은 원리로 원인을 좁힐 수 있다.

## 배운 점

`source ~/.zshrc`는 그동안 안 되면 일단 쳐 보는 명령어였다. PATH가 파일에는 있고 셸에는 없는 상태를 손으로 만들어 보니 이 명령어가 무슨 일을 하는 건지가 분명해졌다. 셸 설정 파일은 설정값을 담은 데이터가 아니라 새 세션이 시작될 때 한 번 실행되는 스크립트라는 걸 알고 나니, 재시작하면 해결되는 비슷한 종류의 문제들도 같은 틀로 이해된다.
